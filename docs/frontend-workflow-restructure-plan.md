## 1. 结论

当前页面的主要问题不是少一个按钮，而是把三个不同层级的工作放进了同一屏：

1. 项目级工作：品牌名、项目介绍、项目注意事项、话题库同步。
2. 批量级工作：勾选文章、批量生成、查看队列、失败重试。
3. 单篇级工作：标题、产品、大纲、正文、人工质检、图片和交付。

重构后按“项目 → 批量/文章列表 → 单篇文章”分层。单篇文章内部不再使用 8 个同权的横向页签，而改为 5 个业务阶段，并在阶段内展示子步骤。

```text
项目中心
└─ 项目工作区
   ├─ 文章任务
   │  └─ 单篇文章工作台
   ├─ 批量处理
   │  └─ 批次详情
   ├─ 交付记录
   └─ 项目设置
```

## 2. 现状问题与直接原因

### 2.1 页面信息层级混杂

- 项目首页的每张项目卡片同时承担“打开项目”和编辑品牌、介绍、注意事项，项目一多就非常长。
- 项目工作台左侧同时放批量按钮、批次进度、12 个状态筛选和任务表格，任务列表被压缩。
- 右侧 8 个页签的业务量不均衡：“人工处理”包含多个环节；“图片”又包含 Word、TDK、打包；“交付”反而只显示文件路径。
- “完全重写”长期放在标题栏的红色主按钮位置，危险操作层级过高。
- 150 篇以上任务和整套编辑状态都在一个约 2700 行的组件中，输入正文时也会连带重渲染任务列表和批次面板。

### 2.2 当前保存并不等于普通保存

- 保存大纲会同时把大纲确认为可生成正文的版本，没有“只存草稿、不确认”的能力。
- 保存正文会同步检查过渡段；缺过渡段时可能调用大模型，最长等待 240 秒，因此一个叫“保存”的按钮可能长时间无响应。
- 保存首图会使已准备的图片、Word、TDK 和交付结果失效，并让流程回退。
- 项目品牌名或项目资料保存后，会更新该项目全部任务的 `revision`；已经打开的文章可能立刻变成旧版本，随后保存返回 409。
- 产品资产处理期间，后端会锁住该任务的其他操作，但前端仍可能显示按钮可用。

### 2.3 当前前端容易产生“卡住”或“选择未生效”的感觉

- 同一文章任意一个请求执行时，其他页签的保存和生成按钮都会被 `isBusy` 一起禁用。
- 产品资产请求可等待 15 分钟，这期间大纲、正文、首图等无关保存也会被锁住。
- 批次状态每 2.5 秒使用 `setInterval` 轮询，没有防止前一请求未结束时再次发起，可能发生请求重叠和结果乱序。
- 接口返回完整任务对象后会整体替换当前任务，可能把其他页签尚未保存的本地草稿覆盖掉。
- 点击“使用产品图片”只改变了本地首图路径；如果未先保存就点击准备图片，后端仍可能使用旧路径。
- 成功和失败消息显示在整页顶部，用户在编辑区下方操作时通常看不到。

### 2.4 当前数据保存有一致性风险

- 大纲、正文和图片的 artifact 文件在 `revision` 冲突检查前写入；如果最终保存返回 409，可能出现“磁盘文件已变化、任务状态未变化”。
- 所有任务保存在一个约 5 MB 的 `tasks.json` 中，读取和保存受全局锁保护，任一保存都需要重写整个文件。批量线程运行时，普通保存和刷新会排队。

这些问题不能只靠换布局解决。页面重排和保存契约稳定化需要分阶段一起做。

## 3. 页面设计原则

1. **项目、批量、单篇分层**：不同作用域的功能不在同一个卡片里竞争空间。
2. **保存与生成分开**：保存只保存；生成、格式修复、抓取、选图等长任务进入后台队列。
3. **业务状态与运行状态分开**：例如同时显示“大纲已确认”和“正文生成中”，不能只用一个状态标签表达两件事。
4. **允许回看和修改**：已完成不等于锁死；已有内容的步骤始终可以进入查看和编辑。
5. **破坏性操作说明影响**：明确显示保留什么、清空什么，再由用户确认。
6. **操作反馈就近显示**：保存中、已保存、失败重试都显示在当前编辑区固定操作栏。
7. **不自动覆盖人工草稿**：后台刷新和批次完成不能覆盖未保存文本。
8. **人工 ZeroGPT 保持人工**：系统提供复制、粘贴、截图、分数和状态记录，不自动访问 ZeroGPT。

## 4. 路由与页面层级

建议形成以下可直接定位、刷新不丢失的地址：

```text
/                                               项目中心
/projects/[customer]                            项目概览或默认跳到文章任务
/projects/[customer]/articles                   文章任务列表
/projects/[customer]/articles/[taskId]?step=... 单篇文章工作台
/projects/[customer]/batches                    批量处理与批次历史
/projects/[customer]/batches/[batchId]          批次详情
/projects/[customer]/deliveries                 交付记录
/projects/[customer]/settings                   项目设置
```

批次失败、运行队列、任务列表中的链接均应跳到具体文章和具体步骤，例如：

```text
/projects/www.qewitfastener.com/articles/task-id?step=outline
```

## 5. 各页面功能分布

### 5.1 项目中心

项目中心只负责找项目和进入项目，不直接展开大段表单。

每个项目卡片或表格行显示：

- 品牌名与官网域名。
- 文章总数、待人工处理数、异常数、已交付数。
- 当前运行任务数。
- 最近更新时间。
- “进入项目”按钮。
- 更多菜单：项目设置、打开项目根目录。

页面顶部保留：

- 搜索项目。
- 刷新。
- 同步话题库。
- 全局运行队列入口。

品牌名、项目介绍和项目注意事项全部移到项目设置页，避免保存一个项目时重置其他项目卡片中的草稿。

### 5.2 项目工作区外壳

进入项目后，顶部固定显示项目身份和一级导航：

```text
← 所有项目 | Qewit Fastener | www.qewitfastener.com

文章任务   批量处理   交付记录   项目设置             运行队列(6)
```

大统计卡仅在项目概览出现。在文章编辑和批量页面，只保留一行紧凑统计，尽量把高度留给列表和编辑器。

### 5.3 文章任务页

文章任务页以“寻找和进入某篇文章”为主，不长期展示整个批量控制台。

```text
┌────────────────────────文章任务────────────────────────┐
│ 搜索 [                    ]  快捷视图  更多筛选  排序    │
│ 待我处理  生成中  失败  可交付  已完成                  │
├─────────────────────────────────────────────────────────┤
│ □ topic_091  话题 / 已选标题      当前阶段     更新时间 │
│ □ topic_092  话题 / 已选标题      正文生成中   批次#18  │
│ □ topic_093  话题 / 已选标题      大纲待确认            │
└─────────────────────────────────────────────────────────┘

勾选后出现固定批量操作条：
已选 12 篇 | 生成标题 | 找产品 | 生成大纲 | 生成正文 | 仅重写正文 | 清除
```

筛选分两层：

- 快捷视图：待我处理、生成中、失败、可交付、已完成。
- 更多筛选：具体业务状态、所属批次、更新时间、是否有异常、是否有未完成交付项。

任务行需要直接显示：

- 业务状态。
- 独立的运行状态和批次编号。
- 失败原因摘要。
- 快速打开具体步骤的入口。

批量操作条只在选择任务后出现，不再永久占据任务列表顶部。

### 5.4 单篇文章工作台

单篇文章使用完整页面，不再把编辑器长期挤在任务列表右侧。桌面端建议采用“左侧阶段导航 + 中间编辑区 + 可收起的右侧资料抽屉”。

```text
┌────────────────────────────────────────────────────────────┐
│ topic_093 · 当前标题                  已保存 14:32          │
│ 业务状态：大纲已确认  运行状态：无     [打开目录] [更多…]  │
├──────────────┬──────────────────────────────┬───────────────┤
│ 1 内容准备    │ 当前子步骤：大纲              │ 文章资料      │
│   标题        │                              │ 原话题        │
│   产品        │ 编辑器 / 选图器 / 表单        │ 竞品链接      │
│   写作要求    │                              │ 产品摘要      │
│ 2 写作        │                              │ 项目要求      │
│   大纲        │                              │               │
│   第一版      │                              │ 可收起        │
│ 3 人工质检    │                              │               │
│ 4 图片        │                              │               │
│ 5 交付        │                              │               │
├──────────────┴──────────────────────────────┴───────────────┤
│ 有未保存修改       [保存修改] [重新生成▼] [版本记录] [下一步]│
└────────────────────────────────────────────────────────────┘
```

顶部“更多”菜单包含：

- 从当前步骤重做。
- 完全重写。
- 查看任务文件。
- 清除可恢复错误。

“完全重写”不再作为红色主按钮长期显示。

#### 阶段 1：内容准备

子步骤：

1. 标题。
2. 产品与官网资产。
3. 本篇写作要求。

标题页显示原话题、竞品标题与竞品链接，候选标题可以重新生成；保存选中标题与重新生成候选是两个按钮。

产品页使用卡片展示：

- 产品名。
- 官网详情页和核验状态。
- 产品描述与参考事实。
- 官网资产数量和已选资产。
- 产品图缩略图。
- 重新抓取、重新选图和人工修改。

写作要求页显示项目介绍和项目注意事项的只读摘要，允许编辑本话题专属要求及自定义补充提示词。“生成时读取哪些资料”在这里配置并独立保存。

#### 阶段 2：写作

子步骤：

1. 大纲。
2. 第一版正文。

大纲页必须同时支持：

- 粘贴或人工编辑大纲。
- 只保存草稿。
- 保存并确认。
- 重新生成大纲。
- 查看版本记录。
- 从大纲重新开始，清空正文以后结果。

第一版页必须同时支持：

- 生成第一版。
- 粘贴外部正文并保存。
- 只重写正文。
- 查看词数与结构校验结果。
- 查看和恢复历史版本。

“保存正文”不得隐式调用大模型。如果需要补过渡段或结构修复，应显示为单独的“检查并修复格式”动作，并进入后台任务。

#### 阶段 3：人工质检

阶段内按真实工作顺序显示四个纵向子步骤：

1. ZeroGPT 初检：复制第一版、填写分数/备注、粘贴或上传截图、确认完成。
2. 降 AI 正文：执行本地提示词，或直接粘贴外部降 AI 文本并保存。
3. ZeroGPT 复检：填写最终分数/备注、粘贴或上传最终截图、确认完成。
4. 链接恢复：以第一版链接为基准校验并回填。

每个子步骤独立显示“待处理、已保存、已确认、需重做”。修改降 AI 正文后，页面应明确提示哪些复检、链接、图片和交付结果会失效。

#### 阶段 4：图片

图片页使用“官网资产库 + 本文已选图片”双栏，不以文件路径输入框作为主要操作。

```text
官网资产库                              本文图片 2/3
[缩略图] 产品名 / 来源详情页            首图槽位
[放大预览] [选为首图] [选为正文图]      [大图预览]

[缩略图] 产品名 / 来源详情页            正文图槽位 1
[放大预览] [选为首图] [选为正文图]      插入位置：标题 + 段落摘要
```

规则：

- 固定三个槽位，首图占一个，整篇最多三张图。
- 候选图显示对应产品名、产品详情页、原始文件名和重复检测结果。
- 首图选择后立即在右侧预览重命名结果“文章标题.webp”。
- 正文图锚点显示“H2/H3 标题 + 目标段落前若干字”，不能只显示标题。
- 提供最终文章图片位置预览，确认图片位于完整段落末尾。
- 路径输入和本地文件上传放进“高级/手动选择”。

主操作改为原子动作“保存选择并准备图片”，避免本地选择尚未保存就用旧路径准备图片。

#### 阶段 5：交付

交付页先显示准备度清单：

```text
✓ 最终正文
✓ 链接校验
✓ 图片与位置
✓ ZeroGPT 最终截图
✓ Word
✗ D 文档                         [生成]
```

操作顺序：

1. 导出或更新 Word。
2. 生成或更新 D.docx。
3. 生成或更新交付包。

结果区显示：

- 正文 Word。
- D.docx。
- 最终 AI 检测截图。
- 最多三张 WebP 图片。
- 打包时间。
- 打开成品目录和重新打包按钮。

### 5.5 批量处理页

批量处理成为独立页面，分为“新建批次、运行中、历史批次”。

新建批次流程：

1. 选择范围：当前筛选、手动勾选、指定状态、复用上一个批次。
2. 选择操作：生成标题、找产品、生成大纲、生成正文、仅重写正文。
3. 执行前预检：可执行数量、会跳过数量、会覆盖数量和具体原因。
4. 确认后加入后台队列。

批次详情示例：

```text
批次 #18 · 批量找产品 · 32/40
运行中 4 | 排队 4 | 成功 29 | 失败 3

topic_006  成功        [打开文章]
topic_020  失败        失败原因… [重试] [打开文章]
topic_093  运行中      [打开文章]
```

全局顶部提供运行队列抽屉。单篇标题、大纲、正文、产品抓取等长任务后续也统一进入此任务中心，发起后用户可以继续处理其他文章。

### 5.6 交付记录页

按文章显示：

- topic 编号和最终标题。
- Word、D 文档、最终截图、图片是否齐全。
- 最近打包时间。
- 打开成品目录。
- 重新打包。
- 缺失项的直接修复入口。

### 5.7 项目设置页

分区保存，不使用一个覆盖全页的全局 busy：

1. 基本资料：官网、品牌名。
2. 项目知识：项目介绍、项目注意事项。
3. 写作默认值：默认资料开关、项目级提示词策略。
4. 文件与同步：话题库来源、输出目录、同步状态。
5. 集成状态：模型、Tavily，仅显示是否可用，不回显密钥。

项目资料保存成功后，已打开文章不能被静默变成不可保存。需要在任务页面提示“项目资料已更新”，并在保存时安全使用服务器最新 revision，或显示可处理的版本冲突。

## 6. 操作语义统一

所有编辑步骤底部采用同一套固定操作栏：

```text
● 未保存 / 保存中 / 已保存 14:32 / 保存失败

[保存草稿] [保存并确认] [重新生成▼] [版本记录] [继续下一步]
```

按钮语义：

| 操作 | 是否调用模型 | 是否推进状态 | 是否清空下游 |
|---|---:|---:|---:|
| 保存草稿 | 否 | 否 | 否 |
| 保存并确认 | 否 | 是 | 按影响提示执行 |
| 重新生成 | 是，后台任务 | 当前步骤完成后更新 | 是，先确认 |
| 从当前步骤重做 | 否 | 回到当前步骤 | 是，先确认 |
| 完全重写 | 否 | 回到待生成标题 | 清空全部业务结果 |

破坏性操作统一使用影响确认框：

```text
重新生成大纲将：
保留：原话题、标题、产品、写作要求
失效：第一版、AI 检测、降 AI 稿、链接、图片、Word、D 文档、交付包

[取消] [确认重新生成]
```

禁用按钮必须显示原因，例如“需要先确认大纲”“产品抓取正在运行”“服务器存在更新”，不能只有灰色按钮。

## 7. 保存与运行可靠性方案

### 7.1 前端状态拆分

- 服务端快照与本地草稿分开保存，接口返回的新任务只更新服务端快照，不重置其他未保存区块。
- 草稿按 `taskId + section` 保存，可临时落到浏览器本地存储，切换文章后仍可恢复。
- pending 状态按具体操作区分，例如 `outline.save`、`outline.generate`、`images.prepare`，不再以整篇文章的 `isBusy` 锁住所有按钮。
- 每个步骤独立显示成功、失败、重试和最后保存时间。
- 批次轮询使用串行 `setTimeout` 或服务端事件；只有存在活动任务时轮询，页面隐藏时暂停。
- 服务端返回新版本且本地有草稿时，显示“服务器有更新”，提供比较、采用服务器版、保留本地版，不能自动覆盖。

### 7.2 长任务统一后台化

以下操作进入任务队列：

- 生成标题。
- 自动找产品和抓取官网资产。
- 模型选择图片。
- 生成或重新生成大纲。
- 生成或重写正文。
- 降 AI 改写。
- 链接恢复。
- 图片转换与排版。
- TDK 生成和较慢的导出任务。

任务需要独立 request id。浏览器超时后显示“后台状态未知，查询结果”，不能让用户直接重复发起同一任务。

### 7.3 后端保存契约调整

1. 大纲拆为“保存草稿”和“确认大纲”，不再由一个 PUT 同时完成两个动作。
2. 正文保存只做持久化和确定性校验，不能调用 LLM；过渡段补写作为单独后台动作。
3. 首图选择与图片准备分开，但提供一个前端原子流程“先保存选择，成功后再准备”。
4. revision 校验必须发生在写 artifact 之前；冲突时不能先改文件再报错。
5. 图片空数组应能明确清空，不能因真假判断而忽略。
6. 后端返回动作可用性时同时返回禁用原因、影响范围和当前运行任务，而不只返回 `allowed_actions` 字符串数组。
7. 中期将单个 `tasks.json` 改为 SQLite 或按任务拆分存储，避免任一保存全量重写所有任务。

### 7.4 版本记录与回滚

现有 `revision` 只用于防止并发覆盖，不是用户可见的历史版本。

需要为标题选择、大纲、第一版、降 AI 稿、链接版和图片选择保存版本快照：

```text
14:32 人工保存 · 1186 词
14:10 模型重新生成 · 1194 词
昨天 17:45 首次生成 · 1178 词
```

版本操作：预览、比较、恢复。恢复前说明会使哪些下游结果失效。

## 9. 推荐实施顺序

### 阶段 0：数据与保存安全

- 修复接口返回整任务覆盖其他未保存草稿。
- 修复首图未保存即可准备图片。
- 修复批次轮询重叠。
- 保存动作改为区块级 pending 和就近反馈。
- revision 校验移到 artifact 写入之前。

### 阶段 1：项目外壳与路由

- 新增项目一级导航和可持久化 URL。
- 项目中心只保留摘要。
- 新增项目设置页。
- 保持现有 API 和功能不丢失。

### 阶段 2：文章列表与批量处理拆分

- 文章任务页全宽化。
- 快捷视图与高级筛选。
- 多选后出现批量操作条。
- 独立批量处理页、批次详情和快速链接。

### 阶段 3：单篇文章 5 阶段工作台

- 内容准备、写作、人工质检、图片、交付。
- 固定步骤操作栏。
- 明确保存、确认、重新生成和从此步重做。
- 禁用原因和影响范围可见。

### 阶段 4：长任务后台化与冲突处理

- 单篇模型、抓取、图片处理接入统一队列。
- 业务状态与运行状态拆分。
- 本地草稿、服务器更新提示和冲突处理。

### 阶段 5：版本、图片和交付体验

- 历史版本预览、比较、恢复。
- 官网资产库、三槽位图片选择和文章位置预览。
- 交付检查清单、交付记录和重新打包。

每个阶段独立构建和测试，确认后再进入下一阶段，不一次性重写全部前后端。

## 10. 验收标准

### 页面结构

- 项目资料不再直接展开在项目卡片中。
- 批量控制台不再永久占据任务列表顶部。
- 单篇工作台按 5 个阶段组织，功能位置与真实工作顺序一致。
- URL 可直接定位文章和步骤，刷新后位置不丢失。

### 编辑与保存

- 保存大纲、正文、首图时只影响当前操作按钮。
- 保存正文不调用模型。
- 任一接口返回不能覆盖其他步骤的未保存草稿。
- 成功、失败和重试在当前步骤内可见。
- 版本冲突不会出现“磁盘已改、页面没改”。

### 重写与回滚

- 大纲和正文无论流程进行到哪一步，都能进入查看。
- 重新生成、从当前步骤重做、完全重写的影响范围清晰可见。
- 历史版本可预览和恢复。

### 批量与运行

- 长任务不会锁住整篇文章或其他文章。
- 批次中的每篇文章都有可持久化快速链接。
- 失败条目能看到原因并单独重试。

### 图片与交付

- 图片以缩略图和大图预览为主，路径输入只作为高级功能。
- 一篇最多三图、首图固定占位、重复图有明确提示。
- 能预览正文图最终插入的标题和段落位置。
- 交付页能一眼看出 Word、D 文档、最终截图和图片是否齐全。
