# ADR-0002：多人运营工作台的部署与知识边界

- 状态：Proposed
- 日期：2026-07-17
- 范围：用户协作、客户项目隔离、知识库存储和部署

## 背景

运营组为多个客户生产文章。不同员工或小组可能负责不同客户项目，同一客户项目也可能经历编辑、复核和交付等多人协作。

当前应用主要面向本地单机运行：配置使用本机知识目录和输出目录，任务与作业使用本地 SQLite，文章资料和导出文件写入本机任务目录。这种形态适合单人操作，但无法自然解决多人共享、权限隔离、统一版本和后台任务持续运行。

## 候选方案

### A. 每位员工完全本地运行

优点：实现和数据边界简单。

缺点：知识重复、版本分裂、无法稳定协作、人员交接困难，不适合运营组共享客户项目。

### B. 云端工作台，知识库保留在员工电脑

优点：私有文件不集中上传。

缺点：云端生成任务必须通过本地连接器查询资料；员工电脑关机、网络变化或版本冲突都会影响任务。还需处理设备认证、同步、缓存、密钥和审计。

结论：第一版不采用。只有明确的数据合规要求禁止集中存储时才重新评估。

### C. 共享工作台和共享项目知识库部署在同一受控环境

优点：统一知识版本、集中权限、持续后台任务、易于交接和审计。每个客户项目通过租户和项目权限隔离。

部署环境可以是公有云、私有云、公司内网服务器或受控 VPC，具体取决于客户资料的数据驻留要求。

结论：推荐，等待数据驻留政策确认后转为 Accepted。

## Proposed Decision

1. 使用 `Organization -> Team -> CustomerProject -> CustomerKnowledgeBase` 作为主要层级。
2. 通过 ProjectMembership 控制用户对客户项目的编辑、复核、查看和管理权限。
3. 客户知识库属于 CustomerProject，而不是某个员工的电脑或个人账户。
4. 前端、API、任务数据、知识索引和对象存储位于同一个受控服务器环境。
5. 私有原始文件、抓取快照、图片和导出物使用对象存储；关系数据和权限使用 PostgreSQL。
6. 知识检索先考虑 PostgreSQL + pgvector，以减少第一版服务数量；通过 KnowledgeIndex 接口保留迁移到独立向量服务的能力。
7. 抓取、解析、Embedding、生成和导出由独立 Worker 执行，不能绑定某位员工电脑是否在线。
8. 所有查询同时带 `organization_id` 与 `project_id` 过滤，禁止跨项目召回知识片段。

## 安全要求

- 传输加密和存储加密。
- API Key 仅保存在服务器端密钥配置中。
- 原始资料和导出文件使用私有访问策略与短期下载链接。
- 记录上传、抓取、发布、检索、生成、导出和删除的审计事件。
- 删除项目时区分逻辑删除、保留期和最终物理清除。
- 备份必须维持 Organization 和 CustomerProject 隔离。

## 尚待决策

- 客户资料能否存放在受控公有云。
- 是否要求公司内网/VPN 才能访问。
- 首批用户数量、并发生成任务数量和资料规模。
- 具体角色权限矩阵与项目交接流程。
